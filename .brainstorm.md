# HR Agentic Core — Architecture & Design Log

This file documents the reasoning and decisions behind the HR intelligence
layer added to kolay-cli. It is updated as the design evolves.

---

## 1. What Was Built

Three new MCP tools and two prompts that implement multi-step HR reasoning
entirely within the existing kolay-cli architecture — no new dependencies,
no new processes.

| Tool | APIs crossed | Output |
|---|---|---|
| `team_availability_analysis` | Unit API × Leave API | Operational risk score + daily absence map |
| `turnover_risk_scan` | Person API × Leave balance API | Risk-ranked employee list |
| `payroll_anomaly_detect` | Transaction API | Duplicate and statistical outlier flags |

| Prompt | Tools it orchestrates | Use case |
|---|---|---|
| `team_risk_brief` | `team_availability_analysis` + `turnover_risk_scan` | Manager briefing for a specific period |
| `hr_trend_analysis` | `turnover_risk_scan` + `payroll_anomaly_detect` | Exec-level quarterly HR report |

All logic lives in `src/kolay_cli/services/hr_analytics.py`. The MCP tools in
`mcp_server.py` are thin wrappers — they apply `@require_auth` and delegate
immediately. This keeps the business logic independently testable.

## 2. Multi-Step Reasoning Design

Each service function follows a documented reasoning plan:

```
Step 1: DATA FETCH — resolve identifiers, call APIs
Step 2: DATA JOIN — cross-reference results from multiple APIs
Step 3: COMPUTE   — derive metrics (ratios, stats, scores)
Step 4: CLASSIFY  — map numeric scores to human labels
```

Every function returns a `reasoning_chain: list[str]` key. Each entry is a
plain-English sentence that narrates what happened at that step, including
intermediate counts and computed values.

**Why this matters for agents**: an LLM receiving the JSON output can read
the `reasoning_chain` to understand *how* the answer was derived — not just
*what* the answer is. This makes the output auditable and allows any model
to explain its reasoning to a human without hallucinating process steps.

Example from `team_availability_analysis`:
```json
"reasoning_chain": [
  "Step 1: Calling unit_tree() to locate unit matching 'Engineering'.",
  "Step 1 result: Matched unit 'Engineering' — 12 member(s) found.",
  "Step 2: Calling leave_list(status='approved', start='2026-03-10', end='2026-03-20', limit=200) and filtering to unit members.",
  "Step 2 result: 3 approved leave record(s) affect this unit in the period.",
  "Step 3: Building daily absence map across the full date range.",
  "Step 3 result: Peak absence 3/12 on 2026-03-15. Average daily absence 1.2. Availability 90.0%.",
  "Step 4: Classifying operational risk from absence ratio and team size.",
  "Step 4 result: Operational risk = 'low' (score=1). Factors: ['≥15 % of team absent simultaneously on 2026-03-15']."
]
```

## 3. LLM-Agnostic Output Contract

All three tools return plain JSON dicts with no model-specific formatting.
The schema is self-describing: every numeric field is accompanied by a string
field explaining what it means (e.g. `risk_score: 3` + `risk_level: "high"`).

Any model that can call MCP tools — Claude, GPT-4o, Gemini, a local Ollama
model — can consume and explain this output without needing prompt engineering
specific to this codebase.

The `reasoning_chain` array doubles as a context-compression mechanism: a
downstream model can summarise the chain instead of re-deriving everything
from raw API responses, saving tokens and latency.

## 4. Risk Signal Catalogue (Turnover Scan)

Signals are declared as a single dict in `hr_analytics.py` (`_SIGNALS`).
Adding a new signal is a one-line change. Current signals and their rationale:

| Signal key | Threshold | Points | Rationale |
|---|---|---|---|
| `unused_critical` | Unused annual leave > 30 d | 3 | Strong burnout predictor (SHRM research) |
| `unused_high` | > 20 d | 2 | Elevated burnout risk |
| `unused_moderate` | > 15 d | 1 | Monitor |
| `new_hire` | Tenure < 6 months | 1 | First-6-months attrition is highest |
| `zero_leave_long` | Tenure > 24 m, 0 d taken | 2 | Disengagement — may be waiting to leave |
| `zero_leave_new` | 0 d taken, any tenure | 1 | May not feel psychologically safe to take leave |

Risk labels: 0 = normal, 1 = low, 2 = medium, 3 = high, ≥4 = critical.

## 5. Operational Risk Classification (Team Availability)

| Peak absence ratio | Score | Label |
|---|---|---|
| ≥ 50 % | 4 | critical |
| ≥ 35 % | 3 | high |
| ≥ 25 % | 2 | medium |
| ≥ 15 % | 1 | low |
| < 15 % | 0 | normal |

Small teams (< 4 members) receive +1 to their score because each absence
represents a proportionally larger operational gap.

## 6. Payroll Anomaly Detection Logic

**Duplicate check**: groups transactions by `(person_id, type, date[:10])`.
Any group with > 1 entry is flagged as a high-severity duplicate.

**Statistical outlier check**: for each transaction type with ≥ 4 data points,
computes `mean` and `stdev` of positive amounts. Any transaction where
`amount > mean + 2σ` is flagged medium-severity.

The 2σ threshold catches roughly the top 2.3 % of a normal distribution.
Types with fewer than 4 observations are skipped — too few data points to
estimate reliable statistics.

## 7. Data Privacy Posture

- No HR data is persisted by these tools. All computation is in-memory for
  the duration of a single tool call.
- The `reasoning_chain` contains aggregate counts and percentages, not raw
  PII (names only appear in `members_on_leave` and `employees` lists that the
  calling agent already has access to via direct API calls).
- Tools are guarded by the same `@require_auth` decorator as all other tools.
  Token resolution follows the existing three-tier priority (request header →
  env var → OS keychain).
- Prompt injection: the `mcp_server.py` system prompt explicitly instructs
  every connected model to treat data fields as UNTRUSTED USER CONTENT.

## 8. Identified API Gaps

The following capabilities would require new Kolay IK endpoints not currently
available in the public API:

| Capability | Gap | Workaround |
|---|---|---|
| Resignation tracking | No "reason code history" endpoint | Infer from termination reason codes in person record |
| Engagement scores | No survey/eNPS data | Proxy using leave utilisation + overtime patterns |
| Recruitment pipeline | No applicant tracking | Out of scope for current API |
| Department-level leave summary | No bulk leave-balance endpoint | Current: N calls (one per employee) — slow for large teams |
| Historical overtime trend | `timelog_list` has no aggregation | Must fetch and aggregate client-side |

The most impactful missing endpoint is a **bulk leave balance** API
(`v2/person/leave-balances?unitId=X`) — adding it would cut `turnover_risk_scan`
from N sequential API calls to 1.

## 9. Extending This Layer

To add a new analytics tool:

1. Write a pure function in `services/hr_analytics.py` that:
   - Accepts plain parameters (no MCP types)
   - Documents its plan as comments
   - Appends to a `chain: list[str]` at each step
   - Returns `{"reasoning_chain": chain, ...}`

2. Add a `@mcp.tool @require_auth` wrapper in `mcp_server.py` that:
   - Has a clear docstring (this becomes the tool description seen by the LLM)
   - Delegates entirely to the service function

3. If the tool orchestrates multiple existing tools, express it as a `@mcp.prompt()`
   instead — the LLM will call the underlying tools itself.

4. Add a test in `tests/` mocking the upstream service calls.
