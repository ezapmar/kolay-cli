## 1. One-Liner

A self-hosted, zero-cloud-dependency AI HR assistant that an enterprise IT team deploys on their own server and hands their HR managers a URL.

---

## 2. Why This Is a Separate Product

Kolay AI Platform (the parent PRD) defines the three-layer architecture: Gateway → RAG → MCP. That architecture assumes the customer connects their own LLM or uses a cloud provider. It's infrastructure-level thinking.

Kolay AI Box inverts the mental model. Instead of "here are the building blocks, assemble them," it says: **"Here is a working AI HR assistant. Deploy it. Use it."**

The inversion matters because:
- Enterprise IT teams want a deployment artifact, not an architecture diagram.
- The sales conversation shifts from "integrate with your AI stack" to "you'll have a working AI HR assistant by end of day."
- It creates a natural upgrade path: start with Box → outgrow it → adopt the full Platform.

This is a **trojan horse product**. The Box gets us inside the enterprise perimeter. Once running, the expansion into RAG (Layer 2), custom models, and advanced analytics happens naturally.

## 3. What It Is

A pre-configured Docker Compose stack that bundles:

```
┌──────────────────────────────────────────────────────────┐
│                    KOLAY AI BOX                           │
│                                                          │
│  ┌─────────────┐    ┌─────────────┐    ┌──────────────┐ │
│  │  Open WebUI  │───▶│  mcpo proxy │───▶│  Kolay MCP   │ │
│  │  (Chat UI)   │    │  (MCP→API)  │    │  Server      │ │
│  └──────┬──────┘    └─────────────┘    └──────┬───────┘ │
│         │                                      │         │
│  ┌──────▼──────┐                       ┌──────▼───────┐ │
│  │   Ollama     │                       │  Kolay İK    │ │
│  │  (Gemma 4)   │                       │  REST API    │ │
│  └─────────────┘                       │  (External)  │ │
│                                        └──────────────┘ │
└──────────────────────────────────────────────────────────┘
```

The user experience:
1. IT deploys the stack (single `docker compose up`)
2. Admin opens `https://ai.company.com`, creates an account in Open WebUI
3. Admin enters their Kolay İK API token in the settings
4. HR managers log in and start asking: "Who is on leave next week?", "Show me the Engineering team's overtime this month", "Submit a leave request for Monday"

## 4. Architecture Decisions

### 4.1 Why Open WebUI

| Requirement | Open WebUI | Custom UI | Verdict |
|-------------|-----------|-----------|---------|
| Time to market | Immediate — mature, production-ready | Months of frontend work | Open WebUI |
| Multi-user auth | Built-in (local accounts, LDAP, OAuth) | Build from scratch | Open WebUI |
| Model management | Ollama integration out of the box | Build integration | Open WebUI |
| MCP support | Native Streamable HTTP + mcpo proxy for stdio | N/A | Open WebUI |
| Customization | Theming, custom prompts, admin controls | Full control | Open WebUI |
| Upgrade path | Users familiar with ChatGPT-like interface | Proprietary lock-in | Open WebUI |
| License | MIT | N/A | Open WebUI |

**Risk:** Open WebUI is a third-party OSS project. Mitigated by the fact that it's MIT-licensed (we can fork if needed) and the actual intelligence lives in Kolay MCP (our code), not the UI.

### 4.2 Why mcpo (MCP-to-OpenAPI Proxy)

Open WebUI supports MCP natively via Streamable HTTP. However, `mcpo` (also by the Open WebUI team, MIT-licensed) provides a cleaner integration path:

- Converts the Kolay MCP server's stdio transport into an OpenAPI-compatible HTTP endpoint
- Generates automatic API documentation at `/docs`
- Handles authentication header injection
- Supports hot-reload of MCP server config without restarting Open WebUI

**Connection topology:**

```
Open WebUI  ──(OpenAPI HTTP)──▶  mcpo  ──(Streamable HTTP)──▶  Kolay MCP Server
                                  │
                              Injects X-Kolay-Token
                              into every request
```

**Alternative path (no mcpo):** Open WebUI can connect directly to Kolay MCP's Streamable HTTP endpoint. This is simpler but requires the MCP server to run in HTTP mode, not stdio. Both paths should be documented; mcpo is the recommended default for Docker Compose deployments.

### 4.3 Why Gemma 4 (Default, Swappable)

Gemma 4 was released April 2, 2026 under Apache 2.0. Key properties:

| Property | Value | Why It Matters |
|----------|-------|----------------|
| License | Apache 2.0 | No commercial restrictions. Enterprise legal won't block it. |
| Tool/function calling | Native support | Essential for MCP tool invocation. Without this, the model can't call `leave_list` or `search_employees`. |
| Multilingual | 140+ languages including Turkish | HR data and conversations will be in Turkish. |
| Sizes | E2B, E4B, 12B, 31B | E4B fits on a laptop for demo. 12B/31B for production on a GPU server. |
| Framework support | Ollama, vLLM, llama.cpp, HF Transformers | Ollama is our default; vLLM for high-throughput. |

**The model is a variable.** The `docker-compose.yml` defaults to Gemma 4 12B via Ollama. Swapping to Mistral, Llama, Qwen, or any Ollama-supported model requires changing one environment variable:

```yaml
OLLAMA_MODEL: "gemma4:12b"  # Change to "mistral:7b", "llama3.3:70b", etc.
```

### 4.4 Token Flow — The Critical Design Detail

The Kolay İK API token is the single credential that unlocks everything. The flow:

```
1. Admin obtains token from Kolay İK  (only Owners/Managers can do this)
                    │
2. Admin enters token in Open WebUI   (stored in Open WebUI's config, per-user)
                    │
3. User sends chat message             ("Who is on leave?")
                    │
4. Open WebUI → Ollama/Gemma 4         (LLM decides to call a tool)
                    │
5. Open WebUI → mcpo → Kolay MCP       (tool call with token in header)
                    │
6. Kolay MCP → Kolay İK REST API       (authenticated with token)
                    │
7. Response flows back to chat UI
```

**Security properties of this flow:**
- Token never leaves the enterprise server (all processing is local)
- Kolay İK's existing RBAC applies — the token carries the user's permissions
- No data sent to any external LLM provider
- Open WebUI's multi-user model means each user can have their own token (different permission levels)

## 5. Deployment Specification

### 5.1 Docker Compose Stack

```
services:
  ollama:          # LLM inference engine
  open-webui:      # Chat UI (port 3000)
  mcpo:            # MCP-to-OpenAPI proxy (port 8000)
  kolay-mcp:       # Kolay MCP server (stdio via mcpo, or HTTP on port 8001)
```

### 5.2 Minimum Hardware

| Tier | Use Case | CPU | RAM | GPU | Model |
|------|----------|-----|-----|-----|-------|
| Demo | Single user, laptop | 8 cores | 16 GB | Apple M-series or none | Gemma 4 E4B (Q4) |
| Team | 5-20 concurrent users | 16 cores | 32 GB | NVIDIA T4 / RTX 4060 | Gemma 4 12B (Q4) |
| Enterprise | 50+ concurrent users | 32+ cores | 64 GB | NVIDIA A100 / L40S | Gemma 4 31B or vLLM with batching |

### 5.3 Setup Flow (Target: Under 15 Minutes)

```bash
# 1. Clone
git clone https://github.com/nicetunca/kolay-ai-box.git
cd kolay-ai-box

# 2. Configure
cp .env.example .env
# Edit .env: set KOLAY_API_TOKEN (or configure per-user in UI later)

# 3. Launch
docker compose up -d

# 4. Open browser
# → http://localhost:3000
# → Create admin account
# → Start chatting with your HR data
```

### 5.4 Configuration Surface

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `KOLAY_API_TOKEN` | Yes (or per-user in UI) | — | Kolay İK API token |
| `OLLAMA_MODEL` | No | `gemma4:12b` | LLM model identifier |
| `WEBUI_PORT` | No | `3000` | Open WebUI port |
| `MCPO_PORT` | No | `8000` | mcpo proxy port |
| `KOLAY_SECURITY_PROFILE` | No | `standard` | `standard` or `enterprise` |
| `WEBUI_AUTH` | No | `true` | Require login |

## 6. User Experience Scenarios

### 6.1 First-Time Setup (IT Admin)

```
Admin deploys Docker stack → opens localhost:3000 → creates account →
navigates to Settings → External Tools → adds Kolay MCP connection →
enters token → tests with "Show me all active employees" → works →
shares URL with HR team
```

### 6.2 Daily HR Manager Use

```
HR Manager: "Who has the most unused annual leave in Engineering?"
AI: [calls search_employees + analyze_employee_wellbeing]
    "3 people have more than 15 unused days: ..."

HR Manager: "Check if Ayşe can take next Friday off"
AI: [calls analyze_leave_impact]
    "Ayşe has 12.5 days remaining. Taking Friday would leave 11.5.
     No team conflicts detected. Shall I submit the request?"

HR Manager: "Yes, submit it"
AI: [calls leave_create]
    "Leave request submitted for Ayşe, April 10."
```

### 6.3 Executive Dashboard Query

```
COO: "Give me a burnout risk summary for the whole company"
AI: [calls turnover_risk_scan]
    "Red zone: 4 employees (>20 unused days, no break in 90+ days)
     Yellow zone: 12 employees (declining timelog regularity)
     Department most at risk: Engineering (3 of 4 red-zone cases)"
```

## 7. Productization Path

### Phase 1: Internal POC (Weeks 1-3)
- Docker Compose stack running on a Kolay server
- Gemma 4 12B via Ollama
- Kolay MCP connected via mcpo
- Test with real Kolay İK data (internal tenant)
- Validate Turkish language quality for HR queries
- Document sharp edges, failure modes, prompt quality

### Phase 2: Packaged Distribution (Weeks 4-6)
- Polished `docker-compose.yml` with sensible defaults
- `.env.example` with documentation
- Setup guide (English + Turkish)
- Pre-configured Open WebUI system prompt optimized for HR assistant persona
- Health check script (`kolay-ai-box doctor`)

### Phase 3: Customer Pilot (Weeks 7-10)
- Deploy at 2-3 enterprise customers
- Gather feedback on: model quality, response accuracy, setup friction, missing tools
- Iterate on system prompts and tool descriptions based on real usage

### Phase 4: Separation & White-Label (Weeks 11-16)
- Extract into standalone repo (`kolay-ai-box`)
- Branding customization (logo, colors, welcome message)
- Admin dashboard: usage analytics, token management, model selection
- Optional: pre-built VM image (OVA) for enterprises without Docker expertise

## 9. Risks Specific to Kolay AI Box

| Risk | Impact | Mitigation |
|------|--------|------------|
| Gemma 4 tool-calling quality insufficient for complex HR queries | High — broken tool calls = bad UX | POC Phase 1 will surface this. Fallback: ship with Mistral or Qwen as alternative. Pre-engineer system prompts with explicit tool-calling examples. |
| Open WebUI MCP integration instability | Medium — breaking changes in OWUI releases | Pin OWUI version in Docker image. Test before upgrading. mcpo provides a stable abstraction layer. |
| Enterprise IT teams unfamiliar with Docker | Medium — deployment friction | Provide OVA/VM image in Phase 4. Ship a one-command installer script. |
| Token management across multiple HR users | Medium — who enters which token? | Document recommended pattern: one "service account" token for read-only tools, individual tokens for write operations. Open WebUI supports per-user tool configs. |
| Model hallucination on HR data | High — wrong leave balances or employee info could cause real problems | All data comes from tool calls to Kolay İK API, not from model memory. Embed "always use tools, never guess HR data" in system prompt. Add disclaimer in UI. |

## 11. Out of Scope

- Multi-tenant SaaS hosting of the Box (that's the Platform)
- Fine-tuning Gemma 4 on HR data (RAG is the answer, not fine-tuning)
- Mobile app (Open WebUI is responsive — good enough for Phase 1)
- Building a custom chat UI (Open WebUI is the UI)
- GPU procurement or hosting for customers (they bring their own server)
