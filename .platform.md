## 1. Problem Statement

Kolay İK has a working MCP server (53 tools, FastMCP 3.x, deployed on Railway) that connects enterprise HR data to any LLM. The current implementation treats every deployment scenario — from a solo HR manager on ChatGPT to a 5,000-employee enterprise running on-prem models — with the same 15-layer security architecture. This is over-engineered for the dominant use case and under-architected for the strategic one.

**The core tension:** We built a secure pipe. We need to build an intelligent platform.

**Current constraints the architecture must respect:**
- Only Owners and Managers can obtain API tokens from Kolay İK. This is the natural authorization boundary — the platform already solves "who can access what."
- MCP exposes no data beyond what the UI shows. There is no privilege escalation vector through the API that doesn't exist through the browser.
- Enterprise customers want to run their own LLMs (data sovereignty, compliance, cost control). We must be model-agnostic.

---

## 2. Strategic Vision: Three-Layer Architecture

The end-state is a platform where Kolay İK becomes the AI-native HR operating system. The mental model is **separation of concerns** — each layer has a single job and scales independently.

```
┌─────────────────────────────────────────────────────────────────┐
│                        ENTERPRISE CLIENT                        │
│              (Any LLM: Gemma 4, Mistral, GPT, Claude)           │
└──────────────────────────┬──────────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────────┐
│  LAYER 1: Multi-Tenant API Gateway & Auth                       │
│  ─ Stateless gateway, tenant-aware routing                      │
│  ─ Rate limiting, billing metering, request logging             │
│  ─ Token validation (existing Kolay İK auth)                    │
└──────────────────────────┬──────────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────────┐
│  LAYER 2: Secure RAG — Tenant-Specific Corporate Memory         │
│  ─ Vector DB with strictly isolated namespaces per tenant        │
│  ─ Employee handbooks, company policies, custom knowledge bases  │
│  ─ Retrieval-only — no model fine-tuning                         │
└──────────────────────────┬──────────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────────┐
│  LAYER 3: Action Execution via MCP (Existing + Evolved)         │
│  ─ Kolay İK REST endpoints exposed as MCP Tools                 │
│  ─ Read: employee data, leave balances, payroll, analytics       │
│  ─ Write: leave requests, shift management, approvals            │
│  ─ Current 53 tools, expanding as API surface grows              │
└─────────────────────────────────────────────────────────────────┘
```

**Key design principle:** The LLM is a variable, not a constant. The POC will use Gemma 4 on a self-hosted server. Production deployments may use any model. The architecture must never couple to a specific inference provider.

## 3. What Changes Now: Security Rationalization

### 3.1 First-Principles Analysis of Current Security Layers

The current 15-layer security stack was designed bottom-up ("what threats exist in the abstract?") rather than top-down ("what is the actual threat model for our product?"). Applying the **principle of proportionate security** — security cost should be proportional to the incremental risk it mitigates:

| Layer | Current State | Verdict | Rationale |
|-------|--------------|---------|-----------|
| L1: TLS/mTLS | TLS on, mTLS optional | **Keep TLS. Drop mTLS from default.** | mTLS adds operational friction (cert management) with no incremental benefit when tokens already authenticate identity. Reserve for enterprise on-prem. |
| L2: Auth (Token/JWT) | Per-tool token check | **Keep as-is.** | This is the right abstraction. Token = identity + authorization. The Kolay İK platform already enforces role-based access. |
| L3: PII Masking | Pseudonymization of names/emails | **Make opt-in, default OFF.** | Users are querying their own data. Masking their own employees' names from their own query is friction, not protection. Useful only when enterprise specifically pipes data through a third-party LLM they don't trust. |
| L4: Field Sanitizer | Whitelist dropping 50+ fields | **Simplify. Align with UI parity principle.** | If the field is visible in Kolay İK's web UI, it should be available via MCP. Drop only fields that are genuinely never shown (raw password hashes, internal IDs with no user meaning). |
| L5: Egress DLP Scanner | TC Kimlik / IBAN redaction | **Keep as opt-in safety net.** | Legitimate for enterprises that need compliance guardrails. But default-on blocks legitimate payroll queries. Make it a toggle. |
| L6: Encrypted Cache | AES-256-GCM in-memory | **Simplify to plaintext in-memory cache.** | The threat model here is "attacker reads server RAM." If they can do that, they can also read the decryption key (it's in the same process). This is security theater for a stateless proxy. A simple TTL cache with tenant isolation suffices. |
| L7: Payload Padding | Anti-traffic analysis | **Remove.** | Protects against nation-state-level traffic analysis on an HR SaaS platform. The attack is theoretical; the overhead is real. |
| L8: Config Encryption | AES-256-GCM with PBKDF2 | **Keep for CLI, unnecessary for server.** | Good for local CLI installations. Irrelevant for cloud-deployed server where config is in environment variables. |
| L9: Rate Limiting | Sliding window per token | **Keep. Promote to default-on.** | Practical protection against runaway LLM loops and abuse. |
| L10: Circuit Breaker | Loop detection | **Keep.** | Essential. Autonomous agents can and do infinite-loop. |
| L11: Activity Logging | Structured JSON to stdout | **Keep. Enhance for billing.** | The foundation of Layer 1's metering capability. |
| L12: HMAC Receipts | Tamper-proof execution receipts | **Make opt-in for enterprise audit.** | Overkill for standard deployment. Valuable for regulated enterprises (banking, healthcare). |
| L13: Tenant Isolation | HMAC-SHA256 cache keys | **Simplify to tenant-prefixed keys.** | Cryptographic isolation of cache keys is unnecessary when the cache is in-process and tenants are already separated by token. Simple `{tenant_id}:{cache_key}` prefix achieves the same isolation without crypto overhead. |
| L14: Prompt Injection Guards | Input filtering | **Keep but reframe.** | Important, but effectiveness depends on implementation. Focus on tool-level validation (type checking, range validation) rather than trying to detect "malicious prompts" — that's the LLM's problem. |
| L15: Human-in-the-Loop | Confirmation for destructive ops | **Keep.** | Right pattern. Destructive actions (terminate, delete) should always require explicit confirmation. |

### 3.2 Resulting Security Profiles

Instead of one monolithic stack, ship two profiles:

**Standard Profile (Default):**
TLS + Token Auth + Rate Limiting + Circuit Breaker + Logging + Human-in-the-Loop + Prompt Input Validation

**Enterprise Profile (Opt-in):**
Standard + PII Masking + DLP Scanner + HMAC Receipts + mTLS + Encrypted Cache + K-Anonymity

Configuration via a single environment variable:
```
KOLAY_SECURITY_PROFILE=standard  # or "enterprise"
```

Individual layers remain toggleable for custom configurations.

## 4. Layer 1: Multi-Tenant API Gateway

### 4.1 Purpose

Transform the current single-server Railway deployment into a proper gateway that routes, meters, and isolates tenant traffic. This is the monetization layer.

### 4.2 Architecture

```
Client (any LLM) ──► API Gateway ──► Kolay MCP Server ──► Kolay İK REST API
                        │
                        ├── Tenant identification (from token)
                        ├── Rate limiting (per-tenant quotas)
                        ├── Usage metering (tool calls, tokens, latency)
                        ├── Request logging (audit trail)
                        └── Billing event emission
```

### 4.3 Key Decisions

- **No separate model hosting (yet).** Layer 1 does not run LLMs. Enterprises bring their own model. The gateway only handles the MCP protocol traffic between their model and Kolay İK data.
- **Stateless.** The gateway holds no session state. Every request is self-contained (token in header → tenant resolved → routed → metered → forgotten).
- **FastMCP 3.x remains the core.** The existing FastMCP server becomes the downstream service behind the gateway. No rewrite.

### 4.4 Implementation Path

| Phase | Deliverable | Timeline |
|-------|------------|----------|
| Phase 1 | Extract tenant ID from token, add per-tenant rate limits | Week 1-2 |
| Phase 2 | Usage metering middleware (tool call counts, response sizes) | Week 3-4 |
| Phase 3 | Billing event emission (webhook to Kolay İK billing) | Week 5-6 |

## 5. Layer 2: Secure RAG — Corporate Memory

### 5.1 Purpose

Allow each tenant to upload company-specific documents (employee handbooks, policies, onboarding guides, internal FAQs) that the LLM can reference when answering HR questions. This transforms the AI from a "data query tool" into an "HR knowledge assistant."

### 5.2 Architecture

```
Tenant Admin uploads docs ──► Document Processing Pipeline
                                    │
                                    ├── Chunking + Embedding
                                    ├── Namespace: tenant_{id}
                                    └── Store in Vector DB
                                    
LLM query ──► Gateway ──► Retrieval (tenant-scoped) ──► Context injection ──► LLM
```

### 5.3 Key Decisions

- **Strict namespace isolation.** Each tenant's documents exist in a physically or logically separated namespace. Cross-tenant retrieval is architecturally impossible, not just policy-prohibited.
- **No model fine-tuning.** RAG only. Documents inform context; they never modify model weights. This is essential for model-agnostic operation (you can't fine-tune Gemma 4 for each tenant and also support Claude).
- **Document types:** PDF, DOCX, plain text. No code execution, no dynamic content.
- **Embedding model:** Decouple from inference model. Use a dedicated embedding model (e.g., `text-embedding-3-small` or open-source `bge-m3` for Turkish language support).

### 5.4 Data Sovereignty Consideration

For Turkish enterprises under KVKK, the vector DB must reside in Turkey or in a jurisdiction with an adequacy decision. Options:
- Self-hosted Qdrant/Weaviate on Turkish cloud (Turkcell Bulut, etc.)
- Managed Qdrant on EU infrastructure (GDPR adequate → KVKK-compatible)

### 5.5 Implementation Path

| Phase | Deliverable | Timeline |
|-------|------------|----------|
| Phase 1 | Document upload API + chunking pipeline | Week 4-6 |
| Phase 2 | Vector DB setup with tenant namespace isolation | Week 6-8 |
| Phase 3 | Retrieval middleware injecting context into MCP responses | Week 8-10 |
| Phase 4 | Admin UI for document management within Kolay İK | Week 10-14 |

## 6. Layer 3: MCP Evolution

### 6.1 Current State (Already Working)

- 53 tools covering CRUD + analytics + wellbeing
- FastMCP 3.x with Streamable HTTP transport
- Deployed on Railway (public multi-tenant endpoint)
- Client configs for ChatGPT, Claude, Gemini, Mistral, Perplexity, Cursor, VS Code, Windsurf, Zed

### 6.2 What Changes

| Area | Current | Target |
|------|---------|--------|
| Security defaults | 15 layers, all-or-nothing | Standard/Enterprise profiles |
| Deployment model | Single Railway instance | Gateway + MCP server (horizontally scalable) |
| Context augmentation | None | RAG-injected context from Layer 2 |
| Billing | None | Per-tool-call metering via Layer 1 |
| Marketplace presence | Manual config | Listed on Anthropic, OpenAI, and other marketplaces |

### 6.3 FastMCP Retention Decision

**Verdict: Keep FastMCP 3.x.** Rationale:
- FastMCP handles MCP protocol, tool registration, transport (stdio + HTTP/SSE), and middleware — exactly what we need.
- Rewriting to a raw ASGI server gains nothing. The protocol layer is not the bottleneck.
- FastMCP's middleware stack allows us to inject gateway concerns (auth, metering, rate limiting) as middleware layers without touching tool implementations.
- The 53 existing tool definitions are FastMCP-native. Migration cost is non-trivial with zero user benefit.

**What to watch:** FastMCP is a relatively young project. If it becomes unmaintained or diverges from MCP spec, we have a clean interface boundary (tool definitions are pure functions wrapping REST calls) that makes migration tractable.

## 7. Marketplace Distribution

### 7.1 Target Platforms

| Platform | Integration Type | Status |
|----------|-----------------|--------|
| OpenAI GPT Store / ChatGPT Apps | Remote MCP connector | ChatGPT integration already working |
| Anthropic Claude Integrations | MCP server listing | Working via claude.ai connectors |
| Anthropic API MCP marketplace | Listed MCP server | Pending marketplace launch |
| Microsoft Copilot Extensions | Plugin / MCP bridge | Research phase |

### 7.2 Marketplace Requirements (Common)

- **OAuth 2.0 or API key auth.** Current token-in-header approach works. May need to wrap in OAuth flow for some marketplaces.
- **Manifest / schema.** The existing `mcp-manifest.json` (JWS-signed) provides server identity. Each marketplace has its own manifest format — generate per-platform.
- **Rate limiting and abuse prevention.** Already in place.
- **Privacy policy and terms.** Required. Draft with reference to KVKK compliance.
- **Branding assets.** Logo, description, screenshots of example interactions.

### 7.3 Kolay CLI / MCP Conversion for Marketplace

The current `kolay-cli` package bundles both CLI and MCP server. For marketplace listing:

- **Extract MCP server into its own deployable unit.** The marketplace endpoint should be the gateway (Layer 1) → MCP server. Not the CLI.
- **Keep CLI as a developer/power-user tool.** CLI remains for local stdio mode, `kolay mcp install`, and direct terminal usage.
- **Shared core:** Both CLI and MCP server import from the same Python package (`kolay-core`). Tool definitions, API client, auth logic live in the shared core.

```
kolay-cli (pip package)
├── kolay-core/          ← Shared: API client, auth, tool definitions
│   ├── api_client.py
│   ├── auth.py
│   └── tools/           ← 53 tool implementations
├── cli/                 ← Typer CLI commands
└── mcp/                 ← FastMCP server + middleware
    ├── server.py
    ├── gateway.py       ← NEW: Layer 1 gateway middleware
    └── rag.py           ← NEW: Layer 2 RAG integration
```

## 8. POC Plan: Gemma 4 + Kolay MCP

### 8.1 Objective

Demonstrate the full three-layer architecture with an open-source, self-hosted LLM. This proves model-agnosticism and gives us a reference deployment for enterprise sales.

### 8.2 Stack

| Component | Choice | Rationale |
|-----------|--------|-----------|
| LLM | Gemma 4 (Google, open-weight) | Strong multilingual (Turkish), self-hostable, no API cost |
| Inference Server | Ollama or vLLM | Ollama for simplicity; vLLM if we need batching/throughput |
| MCP Client | Custom Python script or LangChain agent | Bridges LLM ↔ MCP protocol |
| Vector DB | Qdrant (self-hosted) | Open-source, good performance, namespace isolation |
| Gateway | FastAPI thin layer in front of FastMCP | Tenant routing, metering |

### 8.3 POC Scope

1. Deploy Gemma 4 on a GPU server (or cloud GPU instance)
2. Connect to Kolay MCP server via HTTP transport
3. Demonstrate: "Show me employees on leave this week" → tool call → structured response
4. Demonstrate: "What is our company policy on remote work?" → RAG retrieval → contextual answer
5. Demonstrate: "Submit a leave request for next Monday" → write operation with confirmation

### 8.4 What the POC Proves

- Any LLM that supports tool/function calling can operate as Kolay İK's AI interface
- Enterprise data never leaves the customer's infrastructure (model + gateway + MCP all on-prem)
- The three-layer separation works: swap Gemma 4 for Mistral or Llama — nothing else changes

## 10. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| FastMCP project stagnation | Medium — locked into unmaintained framework | Tool definitions are pure functions. Migration path is clear. Monitor project health quarterly. |
| MCP protocol fragmentation | High — different platforms implement MCP differently | Already observed (ChatGPT lacks custom header support). Maintain per-platform adapters. |
| KVKK enforcement on vector DB hosting | High — regulatory risk for RAG layer | Default to Turkey-hosted or EU-adequate infrastructure. No US-only options. |
| Gemma 4 tool-calling quality | Medium — open models lag behind GPT-4/Claude on function calling | POC will surface this. Fallback: demonstrate with stronger model, optimize prompts for open models. |
| Over-simplifying security | Low — reducing layers could create perception of insecurity | Enterprise profile retains all layers. Marketing emphasizes "right-sized security" not "less security." |
